# 0.4.2 — Demo Game Score

## Goal

Standalone playable proof that 0.4 events plus the 0.4.1 store carry a complete
save-capable game loop with zero scroll listeners in author code. Three
minigames, each **one `Snowfall.ask` call** that pays `0`/`+1`/`+2` when played
live, replays the reader's own saved result when skipped after playing, and
falls back to `+1` when never played. A table of contents whose jumps force
`skip`, exact-viewport spacers that force distance, a running HUD plus a final
tally, and save/load/clear — all as a pure consumer of the public engine API.
`file://` safe, one HTML file, no engine changes.

Depends on: 0.4 (events), 0.4.1 (store + `ask`). This plan supersedes the
`0.4.2-draft` page-global design: the draft's `state.score` and first-wins
logic are deleted, not implemented — keys plus `Snowfall.sum` are the score,
and replay/abandon semantics come from the engine.

## Non-goals

- No new engine API. If the demo needs anything beyond 0.4.1's public surface
  (`ask`/`answer`/`sum`/`exportJSON`/`importJSON`/`reset`/`store`/`refresh`),
  the API is wrong — fix 0.4.1, not the demo.
- No policy showcase: every script uses the defaults (`many`/`forward`/
  `replay`). Policies are proven by the harness `qChoices` probe, not here.
- No wagons, morph, or region dependency. Reads with `wagons=0`; with the
  engine absent or pre-0.4.1 the page is readable prose with idle placeholders,
  score `0`, zero errors (feature-detected, never version-sniffed).
- Not a game framework: one page, three hardcoded minigames, ~150 lines of
  author JS.

## DOM contract

```html
<html data-story="demo-game-score">
<body>
<div id="hud">score <b id="score">0</b> <small id="breakdown"></small>
	<span id="persist"></span>
	<button id="saveBtn">save ↓</button><button id="loadBtn">load ↑</button>
	<button id="clearBtn">clear save</button><button id="selfBtn">self-test</button>
	<input id="loadFile" type="file" accept=".json,application/json" hidden>
</div>
<nav id="toc"><a href="#ch1">1</a> <a href="#ch2">2</a> <a href="#ch3">3</a> <a href="#final">tally</a></nav>
<div id="app">
	<section id="ch1">
		<h2>1 · the toll gate</h2>
		<p>Pay the keeper…</p>
		<div class="game" id="game-1"><p class="idle">…the gate comes into view…</p></div>
		<script type="txt" event="view">askGame(1)</script>
		<script type="txt" event="skip">askGame(1)</script>
	</section>
	<div class="spacer"></div>
	<div class="spacer"></div>
	<section id="ch2"> … askGame(2) … </section>
	<div class="spacer"></div>
	<div class="spacer"></div>
	<div class="spacer"></div>
	<section id="ch3"> … askGame(3) … </section>
	<div class="spacer"></div>
	<section id="final">
		<h2>tally</h2>
		<p id="total">…</p>
		<script type="txt" event="center,end,skip">renderTotal()</script>
	</section>
</div>
```

- Wiring per minigame `k`: `event="view"` → `askGame(k)`, `event="skip"` →
  `askGame(k)` — the *same* call. On `view` it runs live (renders buttons,
  waits for the click); on `skip` the engine runs it in replay mode (resolves
  `saved`/`default` synchronously, renders nothing). This is the draft's open
  question answered by architecture: one call, mode-dependent behaviour.
- `data-story` on `<html>` prefixes the store key (0.4.1 `file://` rule: one
  shared origin for all local documents).
- `#hud`, `#toc`, and the hidden file input live **outside** `#app` — never
  measured as anchors. Save downloads a blob (works on `file://`); load reads
  through the file input (no server, no `prompt()`).
- The final tally declares `event="center,end,skip"`: slow reads render on
  `center` (the `end` re-render is harmless — rendering is idempotent), flicks
  render on `skip`. Every arrival path totals.

## Choice wiring (the one pattern)

```js
function hasAsk() { return !!(window.Snowfall && Snowfall.ask && Snowfall.sum); }
function askGame(k) {
	if (!hasAsk()) return;   // engine absent or pre-0.4.1: stay idle, no error
	var resolved = false;
	Snowfall.ask('gold.ch' + k, 1, null, function (v, mode) {
		resolved = true;
		onGold(k, v, mode);
	});
	if (!resolved) renderButtons(k);   // live only: replay resolved synchronously
}
function onGold(k, v, mode) {
	markPicked(k, v);   // no-op when no buttons are rendered (replay)
	SnowlogSafe('ch' + k + ' pays ' + v + ' (' + mode + ')');
	renderTotal();
}
```

- `options = null`: the author's own buttons own the prompt; clicks call
  `Snowfall.answer('gold.ch' + k, v)`.
- The `resolved` flag is the whole live/replay branch: replay runs `done`
  synchronously inside `ask` (0.4.1), live returns with a pending slot.
  Never render buttons unconditionally — a skip-fired snippet must paint
  nothing.
- `renderTotal()` derives everything from `Snowfall.sum('gold.')` plus the last
  `mode` per key (a page-global *display cache*, never read for logic — logic
  reads the store). Callable from any event, any number of times.
- Re-read semantics, stated on the page: replaying a chapter *overwrites* its
  share (0.4.1 worked case); scrolling past without answering *keeps* it (the
  abandon rule replays `saved`). Re-read to beat your record, skip to keep it.
- `markPicked` after import: picked states re-appear on the next resolution of
  each key; the total is right immediately via `sum`.

## Score semantics

Keys `gold.ch1..ch3`, fallback `1`, total `Snowfall.sum('gold.')`. No
page-global score, no first-wins code — overwrite-same-key plus derived total
is re-pass safe by construction (0.4.1). Breakdown shows `ch1=2 live ·
ch2=1 default · ch3=1 saved ⇒ 4`. HUD also shows the store flag:
`Snowfall.store.persistent ? 'saved ✓' : 'memory only'`.

## Spacer contract

```css
.spacer { height: var(--snow-vh, 100vh); }   /* exactly one engine viewport */
```

- One `.spacer` is exactly one screen: `--snow-vh` is the engine's cached
  `innerHeight`, with a `100vh` fallback when the engine is absent. Stack N
  spacers for N screens of gap.
- Plain block divs: no `overflow`, no positioning, no content. Inside `#app`,
  shifting anchors by design (measured once at load, like any text).

## Engine interaction

- Uses only: `ask`/`answer`/`sum`/`exportJSON`/`importJSON`/`reset`/`store`,
  `refresh()`, `--snow-vh`. Feature-detected (`hasAsk()`); never a version
  compare.
- **Fixed-height rule:** `.game` reserves its height (`min-height: 12rem`), so
  button rendering never moves anchors below and needs no `refresh()`. Any
  author content that *does* change flow height after fire must call
  `Snowfall.refresh()` — stated on the demo page as the one authoring rule.
- TOC jumps are instant scrolls: the synchronous scroll handler fires
  `skip`+`end` for jumped-over chapters in the same frame. No router.
- Cold load mid-document: 0.4 pre-fill latches everything above the fold —
  zero resolutions until re-armed. Stated in the demo header.
- Clear-save recipe (also the self-test's full reset): `scrollTo(0,0)` →
  `Snowfall.reset()` → re-render placeholders idle → `Snowfall.refresh(true)`
  → `renderTotal()`. The order matters: `refresh(true)` anywhere but the top
  would `skip`-resolve everything above the fold. The self-test's
  store-preserving reset is the same recipe minus `reset()`.

## Self-test (in-GUI, no npm)

`self-test` drives the same page and appends PASS/FAIL lines to `<output id="qa">`:

1. Full reset, slow walk `0 → bottom` in 200 px steps, click `+2` whenever
   buttons appear; assert total `6`, all `mode=live`.
2. Full reset, flick `0 → bottom`; assert total `3`, all `default`, no buttons
   ever rendered, `skip`+`end` only (via a `detail.event` counter snippet).
3. Full reset, read `#ch1`, jump `#ch3`; assert `ch2` defaulted, `ch1`/`ch3`
   still playable.
4. After (1), walk bottom → top → bottom without clicking; assert total still
   `6` (abandon replays `saved`, nothing double-grants).
5. Answer `ch1=+2` live, store-preserving reset, flick; assert total `4` with
   `ch1` mode `saved` — the reload-across-visits path without reloading.
6. `exportJSON` → `reset()` → `importJSON` → assert `sum` byte-identical;
   then full reset.
7. Engine-absent by hand (comment the `<script src>`): readable prose, idle
   placeholders, `0`, zero console errors.

## Test matrix (manual)

- Slow read, mixed clicks: HUD updates per click, breakdown matches clicks.
- Flick: all defaults, total `3`, placeholders idle.
- TOC jump over one chapter: that chapter defaults, the landed chapter plays.
- Real reload with a save: flick replays `saved` values (the true 0.4.1 loop).
- Save ↓ then load ↑ the file: totals and modes restored.
- Clear save: back to all-idle, total `0`.
- Reverse scroll: nothing new resolves.
- Reload on `#ch2`: nothing resolves at load.
- `file://` and `http://` both green; DevTools offline; no network requests.

## Acceptance criteria

- [ ] `live`, `saved`, and `default` each demonstrated and labelled per chapter.
- [ ] Running HUD and final tally always agree and equal `sum('gold.')`.
- [ ] TOC jumps skip exactly the jumped-over chapters.
- [ ] Save ↓ / load ↑ round-trips byte-identically; clear save zeroes all.
- [ ] Re-passes without answering never change the score; re-answering
      overwrites exactly that chapter's share.
- [ ] Each `.spacer` measures `innerHeight ± 2 px` with the engine on.
- [ ] Cold load at any scroll position resolves nothing.
- [ ] Engine absent or pre-0.4.1: readable, `0`, zero console errors.
- [ ] Self-test reports PASS on all six scripted checks.
- [ ] No scroll listener, no rAF loop, no `IntersectionObserver` in author code;
      `snowfall.js` untouched by this plan; `qEvents` and `qChoices` green.

## Pitfalls

- A skip-fired snippet must paint nothing: always branch on synchronous
  resolution (the `resolved` flag), never render buttons unconditionally.
- Replaying *is* the grant: totals derive from `sum`, never `+=` — the one
  mistake the engine cannot catch (0.4.1).
- Refresh between prompt and answer (resize, source apply) clears the pending
  slot per 0.4.1: that chapter's buttons stay clickable but `answer` warns and
  is ignored until the chapter re-arms (leave through the bottom) and re-fires.
  Totals stay correct; recovery is one scroll away. Do not paper over it with
  a click-time re-`ask` — double prompts are worse than one stale row.
- The clear-save recipe order (top → reset → idle → `refresh(true)`) is load-
  bearing; `refresh(true)` off the top skip-resolves the chapters above.
- `data-story` is required: without it the key falls back to the pathname tail,
  and two demos in one folder share a wallet.
- Import-then-reread means replay-or-keep (see Choice wiring), not auto-apply —
  that is the documented rule, not a bug.
- HUD/TOC/file-input outside `#app`; no `overflow` on story ancestors.
- Anchor sharing (0.4): each minigame's `view`+`skip` scripts sit adjacent and
  may share an anchor within 1 px — that is what suppresses `skip` after a slow
  pass. Keep minigames further apart (the `.game` box guarantees it).
