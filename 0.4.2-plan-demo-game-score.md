# 0.4.2 — Demo Game Score

## Goal

Standalone playable proof that 0.4 events plus the 0.4.1 store carry a complete
save-capable game loop with zero scroll listeners and zero state writes in
author code. Three minigames, each **one `Snowfall.ask` call** that pays
`0`/`+1`/`+2` when played live, replays the reader's own recorded result when
skipped after playing, and pays the declared fallback when skipped without ever
being played — a chapter the reader flicked past still counts, because the
engine records every resolution and the page only reads `sum('gold.')`. A table
of contents whose jumps force `skip`, exact-viewport spacers that force
distance, a running HUD plus a final tally, and save/load/clear — all as a pure
consumer of the public engine API. `file://` safe, one HTML file, no engine
changes.

Depends on: 0.4 (events), 0.4.1 (store + `ask`). This plan supersedes the
`0.4.2-draft` page-global design: the draft's `state.score` and first-wins
logic are deleted, not implemented — the store's `gold.*` keys plus
`Snowfall.sum` are the score, and skip/abandon semantics come from the engine.

## Non-goals

- No new engine API. If the demo needs anything beyond 0.4.1's public surface
  (`ask`/`answer`/`sum`/`exportJSON`/`importJSON`/`reset`/`store`/`refresh`,
  plus `step()` to drive the self-test), the API is wrong — fix 0.4.1, not the
  demo. In particular the page never writes story state: no `Snowfall.set`, no
  per-chapter bookkeeping. It draws what resolved and reads `sum`.
- No policy showcase: every script uses the defaults (`many`/`forward`/
  `replay`). Policies are proven by the harness `qChoices` probe, not here.
- No wagons, morph, or region dependency. Reads with `wagons=0`; with the
  engine absent or pre-0.4.1 the page is readable prose with idle placeholders,
  score `0`, zero errors (feature-detected, never version-sniffed).
- Not a game framework: one page, three hardcoded minigames, ~200 lines of
  author JS.

## DOM contract

```html
<html data-story="demo-game-score">
<body>
<div id="hud">score <b id="score">0</b> <small id="breakdown"></small>
	<span id="persist"></span>
	<button id="saveBtn">save ↓</button><button id="loadBtn">load ↑</button>
	<button id="clearBtn">clear save</button><button id="selfBtn">self-test</button>
	<input id="loadFile" type="file" accept=".json,application/json" hidden>
</div>
<nav id="toc"><a href="#ch1">1</a> <a href="#ch2">2</a> <a href="#ch3">3</a> <a href="#final">tally</a></nav>
<div id="app">
	<section id="cover"><h1>the toll road</h1><p>three chapters, three bargains …</p></section>
	<section id="ch1">
		<h2>1 · the toll gate</h2>
		<p>Pay the keeper…</p>
		<div class="game" id="game-1"><p class="idle">…the gate comes into view…</p></div>
		<script type="txt" event="view,skip">askGame(1)</script>
	</section>
	<div class="spacer"></div>
	<div class="spacer"></div>
	<section id="ch2"> … askGame(2) … </section>
	<div class="spacer"></div>
	<div class="spacer"></div>
	<div class="spacer"></div>
	<section id="ch3"> … askGame(3) … </section>
	<div class="spacer"></div>
	<section id="final">
		<h2>tally</h2>
		<p id="total">…</p>
		<p><small>the engine's rules, stated for the reader…</small></p>
		<script type="txt" event="center,end,skip">renderTotal()</script>
	</section>
	<output id="qa"></output>
</div>
```

- **The cover is a short title block, on purpose.** A chapter standing inside
  the load viewport fires its `view` in the engine's first frame (0.4), so
  chapter 1 is playable the moment the page opens — no scroll, no lead-in, no
  author workaround. The page does not care whether a given reader's viewport
  puts chapter 1 on screen at load or just below it: both paths are the
  engine's, and the self-test and the node gate cover both.
- **One script per chapter, `event="view,skip"`.** The *same* call runs live on
  `view` (renders the buttons, waits for the click) and in replay mode on `skip`
  (resolves `saved`/`default` synchronously, paints nothing). One tag per
  chapter also keeps the chapter on a single anchor without depending on the
  1-px anchor-sharing rule.
- `data-story` on `<html>` prefixes the store key (0.4.1 `file://` rule: one
  shared origin for all local documents).
- `#hud`, `#toc`, and the hidden file input live **outside** `#app` — never
  measured as anchors. Save downloads a blob (works on `file://`); load reads
  through the file input (no server, no `prompt()`).
- `#breakdown` is one `nowrap` line: the breakdown must not wrap and grow the
  HUD, because the HUD is above every anchor and would shift them all.
- `#qa` sits inside `#app` **below** the tally: the self-test's output cannot
  move anything above it.
- The final tally declares `event="center,end,skip"`; every resolution also
  calls `renderTotal()` directly, so the tally text is current on every arrival
  path (the tag is the re-render, not the only writer).

## Choice wiring (the one pattern)

```js
function hasStore() { return !!(window.Snowfall && Snowfall.ask && Snowfall.sum); }
function askGame(k) {
	if (!hasStore()) return;               // engine absent or pre-0.4.1: stay idle
	var resolved = false;
	Snowfall.ask('gold.ch' + k, FALLBACK, null, function (v, mode) {
		resolved = true;
		mark(k, v, mode);                  // paints the chapter box and the tally
	});
	if (!resolved) prompt(k);              // live only: replay resolved synchronously
}
```

- `options = null`: the author's own buttons own the prompt; a click calls
  `Snowfall.answer('gold.ch' + k, +v)`.
- The `resolved` flag is the whole live/replay branch: replay runs `done`
  synchronously inside `ask` (0.4.1), live returns with a pending slot.
  Never render buttons unconditionally — a skip-fired snippet must paint
  nothing.
- `mark(k, v, mode)` is display only: `values[k]`/`modes[k]`, the chapter box,
  the HUD and the tally. The engine recorded `v` before `done` ran.

## Score semantics

- The store is the score, and the engine fills it: `ask` records the reader's
  live answer and — through the same resolution path as skipping — the fallback
  a skipped or abandoned chapter pays (0.4.1). The page writes nothing.
- Total = `Snowfall.sum('gold.')`; no page-global score, no `+=`, no first-wins.
  One stored value per chapter key, overwritten by the next resolution, is
  re-pass safe by construction.
- The per-chapter *breakdown* reads the last resolution on this pass
  (`values`/`modes` display cache, filled by `mark()`) — never `Snowfall.get`,
  which reads `vars` and knows nothing about ask outcomes.
- Breakdown example: `ch1=2 live · ch2=1 default · ch3=1 saved` ⇒ `4`.
- HUD also shows the store flag:
  `Snowfall.store.persistent ? 'saved ✓' : 'memory only'`.
- `hydrate()` at load reads `exportJSON()` and paints what the store already
  holds: a key in `keys` ⇒ `saved` with the recorded value, or `default` when
  the engine marked it in `defaults`. Display only — it writes nothing,
  resolves nothing, and skips chapters already resolved on this pass. A reload,
  a `load ↑`, or a cold arrival at the tally therefore shows the recorded state
  immediately, labels included.
- Re-read semantics, stated on the page: replaying a chapter *overwrites* its
  share; scrolling past without answering *keeps* it. Clear save resets the view
  and the store, nothing else. Replaying means coming back from the top — a
  re-armed chapter only fires `view` after it has left through the bottom.
- Clearing the save at the top immediately re-arms whatever stands on screen,
  so chapter 1 prompts again within the same frame: the idle placeholders are
  the pre-refresh state, not the resting one.

## Spacer contract

```css
.spacer { height: var(--snow-vh, 100vh); }          /* exactly one engine viewport */
```

- One `.spacer` is exactly one screen: `--snow-vh` is the engine's cached
  `innerHeight`, with a `100vh` fallback when the engine is absent. Stack N
  spacers for N screens of gap.
- Plain block divs: no `overflow`, no positioning, no content. Inside `#app`,
  shifting anchors by design (measured once at load, like any text).
- The title block is ordinary prose: the first chapter needs no lead-in,
  because a chapter standing inside the load viewport fires its `view` in the
  engine's first frame (0.4).

## Engine interaction

- Uses only `ask`/`answer`/`sum`/`exportJSON`/`importJSON`/`reset`/`store`,
  `refresh()`, `step()` (self-test), `--snow-vh`. Feature-detected
  (`hasStore()`); never a version compare.
- `Snowfall.step(y)` drives the self-test at simulated scroll positions: no
  dependence on scroll events or rAF timing, and anchors carry absolute
  document `Y`, so a simulated pass is exact. The page itself does not move
  while the test runs.
- **Fixed-height rule:** `.game` reserves its height (`min-height: 12rem`) and
  `#breakdown` stays one line, so nothing above an anchor changes height after
  a fire and no `refresh()` is needed. Any author content that *does* change
  flow height after fire must call `Snowfall.refresh()` — stated on the page.
- Cold load mid-document: the engine latches every chapter above the viewport
  (no history replay) and fires the ones standing on screen — so a cold arrival
  at the tally resolves nothing below it, and the tally shows the store.
  Stated on the page.
- Clear-save recipe (also the reset between self-test scenarios):
  `scrollTo(0,0)` → `Snowfall.reset()` → re-render placeholders idle →
  `Snowfall.refresh(true)` → `renderTotal()`. The order matters:
  `refresh(true)` anywhere but the top would `skip`-resolve everything above.
- A snippet that the engine can fire in its **first** frame must exist before
  that frame: the page's inline script defines `askGame`/`renderTotal`, and
  `boot()` defers the first `refresh()` to `DOMContentLoaded` while the document
  is parsing — after every inline script.

## Self-test (in-GUI, no npm)

`self-test` exports the reader's save, runs six scenarios through the real page
and appends PASS/FAIL lines to `<output id="qa">`, then restores the save:

1. Slow read from the top, `+2` at every prompt ⇒ total `6`, three `live`, and
   each chapter prompted exactly once (a `view` fires once per chapter).
2. Flick to the tally ⇒ total `3`, three `default`, the flick painted no prompt
   (chapter 1's prompt came from its own load-time `view`, resolved by the
   abandon rule), and no game box is left waiting for a click.
3. Chapter 1 played live, jump to `#ch3` ⇒ `ch2` defaults, `ch3` still prompts
   and plays.
4. Re-read answering `+2` again ⇒ still `6`; a pass without answering ⇒ still
   `6` (nothing double-grants, nothing is lost).
5. Chapter 1 live, then a fresh visit (top + `refresh(true)`, store kept), then
   a flick ⇒ `4` with `ch1` `saved`.
6. `exportJSON` → `reset()` → `importJSON` ⇒ same total.
7. By hand (engine-absent build): readable prose, idle placeholders, `0`, zero
   console errors; the self-test button reports SKIP.

Check 7 is not scriptable from inside the page — the `test/demo-game-score.js`
gate covers the no-engine case in node.

## Test matrix

- `node test/run.js` — the node gate `test/demo-game-score.js` parses the page,
  boots the real engine on the fake DOM (document `loading` → DOMContentLoaded,
  as in a browser), and asserts: the on-screen chapter prompts at load, the slow
  read, the flick and its fallback count, the jump, the fresh visit, the
  re-pass, the save round-trip and clear, the in-GUI self-test output and the
  no-engine case. It fails loudly against the pre-fix page.
- Real browser, manual: slow read with mixed clicks; flick; TOC jump over one
  chapter; real reload with a save (flick replays `saved`); save ↓ then load ↑;
  clear save; reverse scroll; reload on `#ch2`; `file://` and `http://` both
  green; DevTools offline; no network requests.

## Acceptance criteria

- [ ] `live`, `saved`, and `default` each demonstrated and labelled per chapter.
- [ ] **A skipped chapter pays its fallback**: a flick from the top totals `3`,
      not `0`, and the breakdown agrees with the HUD.
- [ ] **Chapter 1 is playable from a cold load**, on both paths: its `view`
      fires at load when the anchor sits inside the first viewport, and on the
      read down when it does not.
- [ ] The page writes no story state: `vars` stays empty over every scenario,
      and the score is exactly `sum('gold.')` over the engine's `keys`.
- [ ] Running HUD and final tally always agree and equal `sum('gold.')`.
- [ ] TOC jumps skip exactly the jumped-over chapters.
- [ ] Save ↓ / load ↑ round-trips byte-identically; clear save zeroes all.
- [ ] Re-passes without answering never change the score; re-answering
      overwrites exactly that chapter's share.
- [ ] Each `.spacer` measures `innerHeight ± 2 px` with the engine on.
- [ ] Cold load at any scroll position: nothing resolves for the chapters above
      the viewport.
- [ ] Engine absent or pre-0.4.1: readable, `0`, zero console errors.
- [ ] `node test/run.js` green, `test/demo-game-score.js` included;
      `qEvents` and `qChoices` green.
- [ ] No scroll listener, no rAF loop, no `IntersectionObserver` in author code.

## Pitfalls

- A skip-fired snippet must paint nothing: always branch on synchronous
  resolution (the `resolved` flag), never render buttons unconditionally.
- **Never keep a second score next to the store.** The engine records every
  resolution; an author-side grant (writing the fallback into `vars`) is added
  to `sum` on top of the recorded key and silently doubles exactly the chapters
  the reader skipped. The page draws the store, it does not top it up.
- Display must read the resolution, not `vars`: `Snowfall.get` reads author
  vars, which know nothing about ask outcomes.
- Replaying *is* the grant: totals derive from `sum`, never `+=` — the one
  mistake the engine cannot catch (every skipped chapter counted twice).
- A snippet that can fire from the engine's **first** frame must be defined
  before that frame runs. In a browser `boot()` defers the first `refresh()` to
  `DOMContentLoaded` while the document is still parsing, after every inline
  script; a page that boots the engine once the document is already complete
  (dynamic inject) owns that ordering itself.
- HUD/TOC/file-input outside `#app`; no `overflow` on story ancestors; the
  breakdown stays one line so a growing HUD cannot move the anchors.
- Clearing the save at the top re-arms whatever stands on screen, so chapter 1
  prompts again right after `clear save` — that is the rule working, not a
  leftover of the previous pass.
